# Live desktop route recovery

The desktop maintains its room's Veilid private route while the application is
running. New and restored rooms use the same `RunningHostRoute` task; it is
owned alongside the room service, independent of Bevy's frame loop. This fixes
a gap identified by comparing the earlier vetchricore listener implementation.
It does not establish the cause of historical public-network timeouts.

`VeilidDeviceNode` forwards local `RouteChange` deaths into a bounded queue of
32 route identifiers. The desktop subscribes before publishing/restoring the
room. Duplicate or unrelated deaths do not require additional publications;
queue overflow conservatively requests recovery. Remote-imported route deaths
do not change the owner's publication.

`HostRouteOwner` retains the current route and at most one candidate:

1. Reopen/read the same encrypted DHT record and validate its entire contents
   against the known current or pending publication.
2. Allocate a candidate with the next route epoch. Preserve room, host identity,
   session epoch, metadata, expiry and the original invitation.
3. Write using the explicitly recovered protected DHT owner capability. A
   same-node client can replace Veilid's default writer when opening a record;
   maintenance must not depend on that mutable node-wide default.
4. Flush and force-read the exact candidate before declaring it published.
   Release the previous route only after that confirmation.

A timeout does not imply the write failed. The candidate remains owned and a
retry reconciles it instead of allocating another route or new invitation.
If a read still finds the exact prior publication, only the same candidate
metadata is written again. A third/conflicting record fails closed. A candidate
that dies during reconciliation still needs replacement after reconciliation.

Each maintenance attempt has a 45-second deadline and transient failures use
1/2/4/8-second backoff (capped at 8 seconds). Allocation is retained separately
across cancelled waits: the upstream allocation future may already have an
internal route under test, so it is not abandoned and restarted on each timeout.
An undeliverable allocation result releases its returned route handle.

Dropping the task requests nonblocking cleanup; explicit `stop()` awaits it.
Record close has a 10-second deadline and known route handles are released on
drop. The desktop node worker also retains the already-locked profile storage
lease through API shutdown and Tokio runtime destruction, so a second process
cannot reuse a namespace while network tasks still own it. Tests cover actual
file locking, failed duplicate startup, explicit shutdown and subsequent
namespace reuse. This is transport cleanup, **not** membership removal, game
disbanding, or creator-independent replication. Those lifecycle requirements
remain in PLAN-6.

Clients refresh a failed route by force-reading the same validated DHT record.
They also reimport an unchanged route epoch: identical DHT bytes prove the
publication, but not that this process still has a usable imported route cache
entry. A changed epoch must preserve room, host, network and session bindings;
the old imported route is released only after the replacement is installed.

No game command is generated by route maintenance. Certified requests, exact
command retries, logical card locations and recipient privacy continue through
their existing adapters. Current route status/errors are redacted; this change
does not yet display route-maintenance status separately in the GUI.

## Evidence and limits

From the repository root:

```powershell
cargo test --locked -p poche-veilid --features device-service,veilid-mock-test,native-input-test --offline --lib --tests
cargo check --locked -p poche-cli --offline
cargo check --locked -p poche-veilid --features veilid --offline
```

The tests exercise allocation failure, lost write replies, failed flush,
successful-but-silent writes, exact-record conflicts, exhausted epochs,
expiry, dead pending routes, queue overflow, cancelled allocation waits,
cleanup, and a shared DHT handle closed by another client. A signed device
service test invalidates a route after a committed seat action and recovers
through ordinary client reads, preserving identity, revision and exact
authorized payload/history before continuing its existing gameplay checks.

The pinned Veilid mock (`99c9616`) does **not** emit `RouteChange` on release or
invalidate imported aliases. Tests explicitly release the stale aliases and
supply the missing lifecycle notification through the production callback.
The `simulate_route_change_for_mock` hook is absent from production builds and
cannot inject game messages. Lower-level fault tests also use the upstream
mock's scoped DHT faults and a private deterministic publication-I/O seam.

The opt-in public test additionally accounts for a pinned-upstream real-API
detail: a creator's allocated route and self-import have the same ID, and route
release prefers the imported entry. Its acceptance-only `debug-api` inspection
checks only whether the exact owned ID is allocated/imported, never logs the
route listing, and fails closed on format drift. It releases the self-import,
then the still-present allocation, and requires Veilid's genuine local-death
callback before accepting a renewed publication. This facility is absent from
normal production features and is not a user/game command.

On September 12, 2026,
`protected_desktop_route_repair_two_process` passed over public Veilid in two
hidden processes in 76.35 seconds. The route advanced from epoch 1 to 2; both
devices completed post-renewal transport reads with the same authorized game
payload, revision, principal/session bindings and invitation, then continued
shared private-safe card motion and abrupt participant restart. A pose reply
timed out after dispatch and was correctly not replayed; the next observation
reconciled the accepted pose. The retained log is
`target/phase6-public-route-06/run.log` (a local build artifact).

This proves public live-route recovery for the tested topology. It does not
prove creator-independent authority replication/failover, universal network
reliability, OS clipboard exchange, or full lifecycle acceptance. No new GPU
capture is needed for this non-rendering slice; the remaining gates are tracked
in [PLAN-6](../PLAN-6-DESKTOP-VEILID.md).
